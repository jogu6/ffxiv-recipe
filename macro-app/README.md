# XIVca マクロ生成機能

既存Webアプリから分離した、FF14製作マクロ生成機能の開発領域です。

## 境界

- `engine/`: ブラウザ入力変換、WASM境界、進捗通知
- `vendor/raphael-sim`, `vendor/raphael-solver`: アプリへ同梱する製作シミュレーターとソルバー
- `web/`: 独立画面と専用Worker
- `tests/`: マクロ機能だけを対象にしたテスト
- `build/`: WASM生成物（Git管理対象外）

既存Webアプリとの接続は、選択中のLodestoneレシピIDを渡して独立画面を開く処理だけに限定します。マクロ機能の通常改修では、既存Webアプリのテストを必要としない構成を維持します。

## 固定した参照条件

製作状態遷移、枝刈り、上限・下限計算、評価およびアクション選択は、Raphael v0.28.6（固定コミット`411168605989d573d89f2d71c01acac9f099e55a`）を基準とします。XIVcaは候補・探索履歴・比較データ・計算表をページ単位で保存し、追加確保に失敗した場合に候補配列を分割します。同じ内容の計算表は完全一致を確認して共有します。退避で候補を捨てたり、完成品質を近似したりしません。アイテム固有情報はLodestone由来のItem.jsonを使用します。

## 確認コマンド

```powershell
cd macro-app
npm run check
```

通常の独立検証ではWASMを再生成しません。WASM境界を変更した場合と統合確認時だけ `npm run check:wasm` を実行します。

## 公開配置

`npm run stage:site` は、Web実行ファイル、WASM成果物、Raphaelのライセンスだけを `site/macro-app/` へ配置します。型定義、パッケージ情報、開発用ファイルは公開領域へコピーしません。`site/macro-app/` は生成物のためGit管理せず、GitHub Pages公開時に最新ソースから再生成します。

WASMは製作状態遷移、完成保証探索、入力変換、進捗通知とページ管理を担当します。JavaScriptは画面操作、保存復元、マクロ文字列化、IndexedDBへの一時保存を担当します。localhost・LANのHTTP・公開HTTPSで同じ保存方式を使用し、Asyncifyによる一時停止・再開を使い、共有メモリーを使わない1スレッドで実行します。保持領域は必要な分だけ増やし、通常はRAM内で探索します。追加確保に失敗した場合に、一部のデータを端末内へ退避して領域を再利用します。1GiBの確保は前提にせず、ページキャッシュの予算はWASM全体やブラウザー全体の使用量とは区別します。

ジョブレベルはジョブ別製作ステータスの必須値です。画面とWASM境界の両方で検証し、各製作アクションの習得可否へ反映します。

通常実行には固定のページキャッシュ上限を設けません。確保失敗を検出した際の回復回数を `storagePressureEvents` として記録します。試験時のキャッシュ予算やWASM上限（512MiBなど）は人工的な設定値であり、スマートフォンで利用可能なメモリーの実測値・推定値ではありません。

生成中の進捗率は経過時間から推測しません。Raphael内部の完了可能性計算、品質上限計算、手数下限計算、最良優先探索の遷移と、探索中の処理済み・生成済みノード数だけを表示へ反映します。

## 生成の計測

開発用の `py tools/serve-local-app.py --bind 0.0.0.0 --port 4173 --directory site` では、マクロ画面への応答にだけ計測送信スクリプトを追加します。`tools/local-sites.ps1` からもこのサーバーを使用します。G66JなどLAN接続した端末から、新しい計測値と画面の応答状況を5秒ごとに自動送信し、`pipeline/reports/macro-profiles/received/` に最新状態JSONと受信履歴JSONLを保存します。通信失敗時は生成を止めず、次回に未送信分を再送します。`http://<開発サーバー>:4173/__local/macro-status` で受信状態と最終受信からの秒数を確認できます。画面の休止や終了で通信が途絶えた場合、受信途絶だけから原因を断定することはできません。

送信・受信処理は `tools/` に置き、GitHub Pages用の `site/` へ配置しません。Python標準の `py -m http.server` にはこの受信機能はありません。サーバー変更の反映には開発サーバーの再起動と端末側のページ再読み込みが必要です。

手動の計測保存ボタンはありません。開発環境では前述の自動送信で記録します。入力条件、データ識別子、実行したWASMのSHA-256、ブラウザー、スレッド数、段階ごとの時刻、探索件数、実キュー件数、WASM確保量、状態復元・Pareto比較・候補展開・統合の累積時間を記録します。最新1回分をブラウザーに約5秒ごとと終了時に保存し、中断後も出力できます。長時間の記録は2400点を超えると間引き、元の時刻と間引き件数を残します。サンプリングはエンジンのコールバック時なので、巨大なバッチの処理中やブラウザーの休止中は更新されません。途中出力の `lastSampleAgeMs` で観測の古さを確認できます。

WASM確保量はOSの物理メモリー使用量ではありません。候補・探索履歴・Pareto・境界計算の論理容量と、RAM上のページキャッシュを分けて記録します。アロケーターの管理領域は内訳に含みません。ページの入出回数と、IndexedDBの実トランザクション数・待ち時間も区別します。OSのスワップ量はブラウザーから取得できず、未測定として明示します。ログの処理別時間は経過時間であり、並列CPU時間の合計ではありません。計測自体のオーバーヘッドは分離測定していません。

リポジトリ直下で `node macro-app/tools/analyze-profile.mjs <計測ログ.json>` を実行すると、CSVと100万件程度ごとの速度・メモリー・処理別時間の集計JSONを隣に出力します。

保存した入力を再現する場合は、`MACRO_PROFILE_INPUT` にログのパスを指定して `npm run test:e2e -- tests/macro-profile-replay.spec.js` を実行します。BraveがインストールされていればBraveで、1スレッドで実行します。`MACRO_PROFILE_LIMIT_MS` は観測時間（既定180000ミリ秒）、`MACRO_PROFILE_TARGET_NODES` は打ち切り件数です。`MACRO_PROFILE_WASM_MIB` と `MACRO_PROFILE_CACHE_MIB` で試験時のWASM上限とページキャッシュ予算を指定し、`MACRO_PROFILE_REQUIRE_COMPLETE=1` で完走を必須にできます。`MACRO_PROFILE_STRESS=all-nq` は中間素材をすべてNQへ変更、`MACRO_PROFILE_STRESS=no-food` は食事・薬品の補正を外す別条件の負荷試験です。変更後の入力と条件名もログへ保存します。`MACRO_PROFILE_REQUIRE_PRESSURE=1` は実際の確保失敗の検出を必須とします。`MACRO_PROFILE_MOBILE=1` は開発用の1GiB上限と協調的休止を適用します。CPU型式・物理RAM・開始時の空きメモリー・電源設定・ブラウザー版・人工的な制限の有無も記録します。過去ログでこれらの条件が不明な場合、生成時間の直接比較には使いません。OS計測を伴う再実行の速度は、アプリ単独実行と同一条件ではありません。

再実行では通常の永続プロファイルを持つ専用ブラウザーを使い、IndexedDBの実ファイル容量とプロセス別CPU時間も記録します。シークレット相当の自動試験環境では退避先までRAM内に保持されるため、低メモリー試験には使いません。Windowsでは物理メモリー使用量・プライベートバイト・ページフォールトとOS全体のページ読み込みを約5秒間隔で別ファイルへ保存します。ページフォールトにはソフトフォールトが含まれ、OS全体のページ読み込みをこのアプリだけのスワップと断定できません。結果は `pipeline/reports/macro-profiles/` に出力します。

開発サーバーで通常のブラウザーを幅600px以下にすると、次の生成から1スレッド・WASM上限1GiB・探索区間間の休止による約4倍の所要時間を目標とした制限を適用します。判定にはマクロパネル幅ではなくブラウザーのページ表示幅を使います。601px以上へ戻した後の生成は通常設定です。実行中の生成条件は途中で変更しません。これはCPUや物理RAMそのものの制限・特定端末の再現ではなく、協調的な休止とWASM確保上限による試験です。長い計算区間の途中では休止できないため、区間ごとの速度は変動します。適用条件と人工的な休止の累積時間を受信ログに残します。これらの処理と試験表示はPythonサーバーが配信時に追加し、本番のファイルには含めません。
