# XIVca マクロ生成機能

既存Webアプリから分離した、FF14製作マクロ生成機能の開発領域です。

## 境界

- `engine/`: ブラウザ入力変換、WASM境界、進捗通知
- `vendor/raphael-sim`, `vendor/raphael-solver`: アプリへ同梱する製作シミュレーターとソルバー
- `web/`: 独立画面と専用Worker
- `tests/`: マクロ機能だけを対象にしたテスト
- `build/`: WASM生成物（Git管理対象外）

既存Webアプリとの接続は、選択中のLodestoneレシピIDを渡して独立画面を開く処理だけに限定します。マクロ機能の通常改修では、既存Webアプリのテストを必要としない構成を維持します。

## 固定した参照条件

製作状態遷移、枝刈り、上限・下限計算、評価およびアクション選択は、Raphael v0.28.6（固定コミット`411168605989d573d89f2d71c01acac9f099e55a`）を基準とします。XIVcaは候補・探索履歴・比較データ・計算表をページ単位で保存し、連続メモリーの確保に失敗した場合は退避可能な配列へ移します。同じ評価の候補を全体で比較してから探索を進め、保存上の分割によって比較範囲を変えません。RAM内の比較では、同じキーの比較中だけ葉の値を作業配列へ読み、完了時に退避可能なページへ戻します。作業配列を確保できない場合はページごとに排他制御して比較します。同じ内容の計算表は完全一致を確認して共有します。退避で候補を捨てたり、完成品質を近似したりしません。アイテム固有情報はLodestone由来のItem.jsonを使用します。

## 確認コマンド

```powershell
cd macro-app
npm run check
```

通常の独立検証ではWASMを再生成しません。WASM境界を変更した場合と統合確認時だけ `npm run check:wasm` を実行します。

## 公開配置

`npm run stage:site` は、Web実行ファイル、WASM成果物、Raphaelのライセンスだけを `site/macro-app/` へ配置します。型定義、パッケージ情報、開発用ファイルは公開領域へコピーしません。`site/macro-app/` は生成物のためGit管理せず、GitHub Pages公開時に最新ソースから再生成します。

WASMは製作状態遷移、完成保証探索、入力変換、進捗通知とページ管理を担当します。JavaScriptは画面操作、保存復元、マクロ文字列化と端末内への一時保存を担当します。共有メモリーが利用できる環境では論理プロセッサ数の半分（切り捨て）に1を加えた数（総数未満、総数が1または不明なら1）で並列実行し、一時保存は専用Workerが処理します。共有メモリーが利用できない環境では、Asyncifyによる一時停止・再開を使って1スレッドで実行します。GitHub Pagesの初回表示など、まだ分離ヘッダーが有効でない文書を強制再読み込みすることはありません。

OPFSを利用できる環境では、生成開始時に合計3GiBのファイル領域を準備し、探索中には拡張しません。分割サイズを64MiBより4KiB小さくして、WebKit内部の容量の丸めによる過剰な割当を避けます。準備時には各ファイルの末尾を書き込んで確認しますが、3GiB全体への書き込みは検証用だけで行います。OSの空き容量は途中でも変化するため、実際の読み書きの失敗も検出します。Safariでは削除済み領域が推定使用量に残る場合があるため、OPFSの確保可否をその推定値だけでは判定しません。OPFSが使えないHTTP LANなどではIndexedDBへ切り替えます。この代替経路では3GiBを論理上限として扱い、全領域の事前確保を保証しません。

確保できる間は探索ページをRAMに保持します。同じ評価の候補は、全件を比較してからまとめて探索・統合します。作業配列の連続確保に失敗した場合も、件数で比較範囲を区切らず、退避可能な配列へ移します。WASMの探索履歴と待機候補は、32ビットの索引とアクションを5バイトで欠落なく保持します。計算表は共有読み取りで参照し、不変の表と問い合わせ結果をスレッド内で正確に再利用します。候補の復元では、同じ履歴番号の途中状態を再利用します。いずれも元データは保持し、キャッシュの衝突時は元データから計算します。退避ページが必要な場合だけ読み取りロックを解放して読み戻します。確保に失敗した場合は退避可能なページを解放し、必要な索引は一度だけ再確保を試みます。再び不足した場合も同じ回復処理を行い、同じ要求を無制限に繰り返さず、回復不能ならエラーを返します。中止時は計算Workerを止め、保存領域の準備・入出力の終了を待って、その生成が作成した一時ファイルを削除します。

ジョブレベルはジョブ別製作ステータスの必須値です。画面とWASM境界の両方で検証し、各製作アクションの習得可否へ反映します。

WASMのメモリー拡張は、空きがある間は16MiB単位で行い、拡張回数と他スレッドの確保待ちを減らします。標準ライブラリーと同じdlmalloc 0.2.13を使い、実際に確保した領域全体を再利用します。まとめた拡張に一度失敗すると、その生成では以降、必要最小のページ数だけを要求します。その要求にも失敗した場合に退避・回復へ進みます。拡張の呼び出し回数・失敗回数・確保量も計測します。

通常実行には固定のページキャッシュ上限を設けません。メモリーが十分ある環境では探索データの退避を行わず、実際の確保失敗を検出した後だけ退避へ切り替えます。保存領域の準備はRAM容量にかかわらず開始時に行います。回復回数を `storagePressureEvents` として記録します。試験時のキャッシュ予算やWASM上限は人工的な設定値であり、スマートフォンで利用可能なメモリーの実測値・推定値ではありません。

生成中は完了率を表示しません。Raphael内部の処理段階、実際に確認した候補数、端末への一時保存の現在使用量を表示します。読み込みの累計量と最後の進行確認時刻は開発環境だけに表示します。状態表示のために計算を待機させる処理はありません。

マクロパネルでは、レシピ別に食事・薬品・中間素材HQの選択、編集中のジョブ、各欄の開閉状態とリスト内位置を保存します。再読み込み時は内容を復元してからパネルの保存位置へ戻します。既存の保存済みマクロしかない場合は、その生成条件から選択を引き継ぎます。保存済みマクロは、データ版・製作ステータス・選択条件が一致する場合に表示します。

不具合報告は、本番でも保持する端末内の記録から出力します。全記録の要約・最大値・時系列とブラウザーの容量推計を出力時に集計し、開発専用の記録は分けて表示します。JavaScriptの識別子はビルド時に付与します。報告項目の追加に伴う生成中の計測頻度・保存頻度の変更はありません。

## 生成の計測

開発用の `py tools/serve-local-app.py --bind 0.0.0.0 --port 4173 --directory site` では、マクロ画面への応答にだけ計測送信スクリプトを追加します。`tools/local-sites.ps1` からもこのサーバーを使用します。G66JなどLAN接続した端末から、新しい計測値と画面の応答状況を5秒ごとに自動送信し、`pipeline/reports/macro-profiles/received/` に最新状態JSONと受信履歴JSONLを保存します。通信失敗時は生成を止めず、次回に未送信分を再送します。`http://<開発サーバー>:4173/__local/macro-status` で受信状態と最終受信からの秒数を確認できます。画面の休止や終了で通信が途絶えた場合、受信途絶だけから原因を断定することはできません。

送信・受信処理は `tools/` に置き、GitHub Pages用の `site/` へ配置しません。Python標準の `py -m http.server` にはこの受信機能はありません。サーバー変更の反映には開発サーバーの再起動と端末側のページ再読み込みが必要です。

手動の計測保存ボタンはありません。開発環境では前述の自動送信で記録します。入力条件、データ識別子、実行したWASMのSHA-256、ブラウザー、スレッド数、段階ごとの時刻、探索件数、実キュー件数、WASM確保量、状態復元・Pareto比較（キー別の並べ替え・実際の比較の内訳を含む）・候補展開・統合の累積時間、計算表の問い合わせをキャッシュで処理した件数と元の表を読んだ件数（完了時）を記録します。最新1回分をブラウザーに約5秒ごとと終了時に保存し、中断後も出力できます。長時間の記録は2400点を超えると間引き、元の時刻と間引き件数を残します。サンプリングはエンジンのコールバック時なので、巨大なバッチの処理中やブラウザーの休止中は更新されません。途中出力の `lastSampleAgeMs` で観測の古さを確認できます。

生成画面の「端末への一時保存」は、現在有効な退避データの容量と準備した容量を表示します。再利用や読み戻しを含む累計書き込み量ではありません。保存と読み込みで説明文は切り替えません。読み込みの累計量と最後の進行確認時刻は開発環境だけに表示します。不具合報告には本番環境でも、保存方式、OPFSのファイル準備とIndexedDBの論理上限の区別、実使用量、退避位置の最大到達量、累計I/O量、準備・終了の記録、失敗した処理と後片付けのエラーを含めます。ブラウザーが報告するオリジン全体の使用量は別の推計値として記録します。

WASM確保量はOSの物理メモリー使用量ではありません。候補・探索履歴・Pareto・境界計算の論理容量と、RAM上のページキャッシュを分けて記録します。アロケーターの管理領域は内訳に含みません。ページの入出回数と、IndexedDBの実トランザクション数・待ち時間も区別します。OSのスワップ量はブラウザーから取得できず、未測定として明示します。ログの処理別時間は経過時間であり、並列CPU時間の合計ではありません。計測自体のオーバーヘッドは分離測定していません。

リポジトリ直下で `node macro-app/tools/analyze-profile.mjs <計測ログ.json>` を実行すると、CSVと100万件程度ごとの速度・メモリー・処理別時間の集計JSONを隣に出力します。

保存した入力を再現する場合は、`MACRO_PROFILE_INPUT` にログのパスを指定して `npm run test:e2e -- tests/macro-profile-replay.spec.js` を実行します。BraveがインストールされていればBraveで、1スレッドで実行します。`MACRO_PROFILE_LIMIT_MS` は観測時間（既定180000ミリ秒）、`MACRO_PROFILE_TARGET_NODES` は打ち切り件数です。`MACRO_PROFILE_WASM_MIB` と `MACRO_PROFILE_CACHE_MIB` で試験時のWASM上限とページキャッシュ予算を指定し、`MACRO_PROFILE_REQUIRE_COMPLETE=1` で完走を必須にできます。`MACRO_PROFILE_STRESS=all-nq` は中間素材をすべてNQへ変更、`MACRO_PROFILE_STRESS=no-food` は食事・薬品の補正を外す別条件の負荷試験です。変更後の入力と条件名もログへ保存します。`MACRO_PROFILE_REQUIRE_PRESSURE=1` は実際の確保失敗の検出を必須とします。`MACRO_PROFILE_MOBILE=1` は開発用の1GiB上限を適用します。人工的な休止は行いません。CPU型式・物理RAM・開始時の空きメモリー・電源設定・ブラウザー版・人工的な制限の有無も記録します。過去ログでこれらの条件が不明な場合、生成時間の直接比較には使いません。OS計測を伴う再実行の速度は、アプリ単独実行と同一条件ではありません。

再実行では通常の永続プロファイルを持つ専用ブラウザーを使い、IndexedDBの実ファイル容量とプロセス別CPU時間も記録します。シークレット相当の自動試験環境では退避先までRAM内に保持されるため、低メモリー試験には使いません。Windowsでは物理メモリー使用量・プライベートバイト・ページフォールトとOS全体のページ読み込みを約5秒間隔で別ファイルへ保存します。ページフォールトにはソフトフォールトが含まれ、OS全体のページ読み込みをこのアプリだけのスワップと断定できません。結果は `pipeline/reports/macro-profiles/` に出力します。

開発サーバーで通常のブラウザーを幅600px以下にすると、次の生成から1スレッド・WASM上限1GiB・探索ページのRAM保持上限512MiBを適用します。人工的な休止は行いません。既知の1GiB上限の半分を索引・作業配列・WASM本体に残すため、探索ページは確保失敗を待たずに退避します。判定にはマクロパネル幅ではなくブラウザーのページ表示幅を使います。601px以上へ戻した後の生成は通常設定です。実行中の生成条件は途中で変更しません。これはCPUや物理RAMそのものの制限・特定端末の再現ではありません。これらの処理と試験表示はPythonサーバーが配信時に追加し、本番のファイルには含めません。

メモリー拡張は実行時の設定上限を参照し、上限を超える要求は実行前に回避します。確保済みの領域は引き続き再利用でき、小さい追加要求まで禁止しません。`wasmMemoryGrowFailures`は実際に拡張を試して失敗した回数、`wasmMemoryLimitAvoided`は既知の上限超過を事前回避した回数です。要求サイズ・要求前の確保量・上限・処理段階・結果を最大64件保持し、報告用情報にも含めます。記録は確保処理内では固定配列に保存し、JSON化は確保処理のロックを解放してから行います。


単独エンジンは候補の復元・並べ替え・比較・統合と準備計算について、実際に処理した作業量を途中通知します。通常のループでは4096件単位と作業の開始・終了を観測し、小さなグループはまとめて計測します。通知は最大毎秒2回に抑え、通知のための待機や探索範囲の分割は行いません。並列エンジンではこの通知呼び出しをコンパイル時に除外します。画面の「今回の作業の進み具合」は現在の作業範囲内の割合で、全生成の完了率ではありません。作業が変わると割合は新しい範囲の値になり、細かな作業名は報告用情報に保持します。同じ表示内容での再描画を省きます。

`storageSolverWaitMs`は単独エンジンが非同期保存の完了を待って計算を中断した経過時間、`storageSolverWaitCount`は回数、`storageSolverMaxWaitMs`は最長の1回です。既存のAsyncify待機を測定し、追加の待機は行いません。OPFS同期読み書きではこの非同期待機は0で、保存APIに費やした時間は`storageReadMs`／`storageWriteMs`、書込反映は`storageFlushMs`／`storageFlushCount`に記録します。保存APIの時間と非同期待機には重複があるため加算できず、OSのCPU待機時間を表す値でもありません。
